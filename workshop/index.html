Ship a domain AI agent to a real URL in one hour.

Each attendee forks the skeleton repo, opens VS Code with GitHub Copilot, and ships four features across four branches. Every merge to main triggers an automatic deploy on Dokploy to the attendee's own URL. By the end, everyone has a working chat-over-IBP-data app they can hand to a planner.

Prerequisites

Send this list 48 hours before the workshop.

  • A GitHub account with an active Copilot license. The only credential the deployed app needs to call Claude / GPT / Gemini.
  • Visual Studio Code with the GitHub Copilot extension. The in-editor Chat is what drives every implementation step.
  • Git installed and signed in to GitHub (either gh auth login or HTTPS credentials in Git Credential Manager). Needed to push branches.
  • A Copilot-scoped GitHub token saved in your Dokploy project as GITHUB_TOKEN. The deployed app reads it at runtime to talk to the Copilot API.
    1. Generate it once on your machine. First sign in to GitHub via the CLI as the account that owns your Copilot license (skip if gh auth status already shows you signed in as that account): 
      gh auth login
      Then add the copilot scope and print the token: 
      gh auth refresh --scopes copilot
gh auth status --show-token
      Copy the value shown on the Token: line (starts with gho_… or ghu_…).
    2. In Dokploy: open your application → Environment tab → Add Variable. Paste a single line in the form: 
      GITHUB_TOKEN=<your token>
      Replace <your token> with the value you copied (no quotes, no spaces). Save.
    3. Click Redeploy. Once healthy, visit https://<your-domain>/api/models — you should see every model your GitHub organisation has enabled for Copilot (3 models in the Opella case). If you only see 0 or an error payload, the token is missing or lacks the copilot scope.
    Never commit the token. Rotate with the same gh auth refresh command if it leaks.
  • Your Dokploy project URL — the facilitator provisions one per attendee and emails it the day before. This is where merges deploy to.

Node.js is not required. The app runs on Dokploy, not your laptop. If you want to preview a change locally before pushing, install Node 22 LTS and run npm install && npm run dev — but the workshop does not depend on it.

The deploy loop

The same five-step cycle repeats for every feature.

git checkout -b feat/x
→
Copilot writes code
→
git push
→
PR + merge
→
Dokploy deploys
→
Refresh your URL
About 60–90 seconds from merge to live. Attendees run this loop five times in one hour.

Context

Opella's Integrated Business Planning cycle moves tens of thousands of forecast rows every month across 44 AMEA countries, 7 zones, and ~50 brands. Today, when a planner wants to know what moved between last cycle and this cycle, and why, the answer lives in a TM1 extract, a few pivot tables, and the heads of two or three people. Surfacing one exception can take an afternoon. Surfacing the right exception in time for the Demand Review is the difference between a decision and a postponement.

The goal of this project is to give every Opella supply chain person a small, owned, deployable AI agent that sits on top of their own operational data and answers planner-grade questions in seconds — using only the GitHub Copilot license they already have. No Foundry, no Azure provisioning, no ML team in the loop. One license, one repo, one URL.

The goal of this workshop is to prove that loop end-to-end on a synthetic IBP dataset. By the time you walk out of the room you will have shipped four features to a public URL using GitHub Copilot, and you will know exactly which file to change to point the same agent at your own data on Monday morning.

"What you ship in this workshop is what you take back to your team. Every feature is a branch you cut, a prompt you give Copilot, and a merge that goes live in 90 seconds. We do that four times."

Fork the skeleton & confirm your URL

Steps

  2. Clone the fork locally: git clone https://github.com/<you>/opella-ibp-skeleton.git
  3. Open the folder in VS Code. Verify the Copilot extension is signed in (status bar bottom-right).

2

Feature 1 — Model picker

8 min

First trip around the deploy loop. Replace the hard-coded model with a dropdown of every model the Copilot license can reach.

Concept (HoL Level 3 — Code Generation)

This is the simplest use of Copilot Agent mode: hand it a small, well-scoped multi-file edit and let it ship. The goal is to feel the loop, not to write impressive code.

Why it matters

Different planner questions deserve different models. "Summarise this cycle in three bullets" is a job for a cheap, fast model; "reconcile these four cycles and explain the divergence" is a job for a frontier reasoning model. Hard-coding one wastes the rest of the Opella Copilot license. This feature makes the agent model-portable from day one.

Branch & prompt

git checkout -b feat/model-picker
In app/lib/copilot.server.ts there is already a getClient() singleton. Add a new exported function listModels() that calls client.listModels() and returns [{ id, name }]. Then create app/routes/api.models.ts that exports a loader returning { models }. Update app/routes/home.tsx to fetch /api/models in a useEffect, render a <select> next to the input, and send the chosen model in the POST body to /api/chat. Register the new route in app/routes.ts.

Ship

git add -A && git commit -m "feat: model picker" && git push -u origin feat/model-picker

Merge the PR. Watch Dokploy redeploy. Refresh — the dropdown is there.

Re-test the same prompt

Pick a small/fast model (e.g. gpt-4o-mini) and ask the exact same question you asked before:

Summarise this IBP cycle for AMEA in three bullets.

Now switch the dropdown to a frontier reasoning model (e.g. claude-sonnet-4.5 or gpt-5) and re-send. The voice, length, and depth of the answer change visibly — same prompt, different model, no code change. The agent is now model-portable.

Done when:
  • The URL shows a model dropdown populated with every model your GitHub organisation has enabled for Copilot (3 models for Opella).
  • Switching models and re-asking the same question returns answers in different voices.
3

Feature 2 — Inject the IBP data context

12 min

Turn a generic chat into a domain agent. The model now answers using the real synthetic IBP numbers, every turn.

Concept (HoL Level 3 — Refactoring + Role Prompting)

Two HoL techniques applied at once: agent-mode multi-file refactoring (create the prompt module, wire it into the chat action) and role prompting — telling the model exactly who it is, what data it may use, and what answer shape is acceptable.

Why it matters

A generic chatbot tells a planner what "IBP" stands for. A grounded agent tells them "Net Sales for ANZ dropped €4.2M between IBP Jan and IBP Feb, mostly carried by Australia and concentrated in two brands — here is what to validate before the Demand Review." The difference is whether the model is allowed to invent or forced to cite. We do this with a static JSON file — no vector DB, no retraining. The same pattern works for any structured operational dataset.

Try it first (before you implement)

On your live URL — with any model picked — ask a specific, grounded question:

What is Net Sales for ANZ in the latest IBP cycle, in EUR millions? And which zone moved the most vs the previous cycle?

Watch what comes back. You will see one of three failure modes: (a) the model refuses because it has no data, (b) it gives a generic IBP explainer, or (c) it invents a number that looks plausible. None of those are usable in a Demand Review. The model has no access to your dataset — it is guessing. This feature gives it one.

Branch & prompt

git checkout main && git pull && git checkout -b feat/ibp-context
The file public/ibp-data-summary.json contains a structured summary of the AMEA IBP dataset. Create app/lib/prompts.server.ts that: (1) reads the JSON once on startup and caches it; (2) exports buildDataContext() returning a Markdown block under 1,500 characters with three tables (meta header, Net Sales overview, zone-level breakdown); (3) exports a SYSTEM_PROMPT constant that names the persona "IBP demand-review analyst for Opella AMEA", restricts the model to the data in the CONTEXT block, requires EUR millions to one decimal, and forces the answer shape what changed → why → what to validate. Then update app/routes/api.chat.ts so the action composes SYSTEM_PROMPT + "\n\nCONTEXT:\n" + buildDataContext() and passes it as the systemMessage when creating the Copilot session.

Ship & verify

git add -A && git commit -m "feat: inject IBP data context" && git push -u origin feat/ibp-context

Merge. Wait ~90s. Refresh.

Re-test the same prompt

Ask the exact same question you asked before the implementation:

What is Net Sales for ANZ in the latest IBP cycle, in EUR millions? And which zone moved the most vs the previous cycle?

The answer is now a specific zone, a specific number in EUR millions to one decimal, and follows the what changed → why → what to validate shape. Then push it harder:

Which countries moved the most between the last IBP cycle and this one? Top three with delta in EUR millions, plus your best guess at the driver.

This is the moment the chat becomes an agent. Same model, same prompt as before — but a completely different class of answer, because the model now has the data and the persona.

4

Feature 3 — Plan-then-implement with tests

10 min

Use Plan mode to design a small feature, then hand the plan to Agent mode to implement it with unit tests in one flow.

Concept (HoL Level 4 — Plan & Implement, plus L3 Tests generation)

Agent mode without a plan tends to over-edit. Plan mode reads the codebase, proposes a structured TODO, asks clarifying questions, and only then hands off to Agent to ship. The deliverable here is a tiny but real one: a server-side helper that ranks the top movers, plus Vitest tests — the kind of code you do want test coverage on the day a planner cites the output in a Demand Review.

Why it matters

The fast path — "just ask Agent" — works for trivial edits and collapses for anything else. Plan-mode is the difference between an agent that ships your idea and one that ships its idea. And once you ask for tests up front, you stop merging code that hallucinates a column name your dataset doesn't have.

Tests gate the deploy. The skeleton's Dockerfile runs npm test --if-present during the build stage. Before this feature there is no test script, so the step is a no-op and deploys go through. The moment you add Vitest and a "test" script in package.json, every Dokploy build runs the suite — and a single failing test fails the build and blocks the deploy. From now on, broken tests never reach your URL.
Try it first (before you implement)

On your live URL ask:

Show me the top movers across AMEA this cycle, ranked by absolute Net Sales delta in EUR millions.

The agent has zone-level data from Feature 2 but no ranking helper. The answer will be vague ("a few zones moved noticeably"), or it will eyeball the zone table and miss country-level granularity, or it will return an ordering that disagrees between runs. Also try, from your local clone:

npm test

There is no test script yet, so npm prints "Missing script: test". The Dockerfile's npm test --if-present step is currently a no-op — nothing protects main from a regression.

Branch & flow

git checkout main && git pull && git checkout -b feat/top-movers

Open a new Copilot Chat in Plan mode (premium model: GPT-5 or Claude Sonnet 4.5). Paste:

I want a new server-only helper app/lib/movers.server.ts exporting topMovers(n: number) that reads the cached IBP summary and returns the n countries with the largest absolute Net Sales delta between the two most recent IBP cycles, as { country, zone, deltaMEur, direction }[]. Wire it into buildDataContext() as a fourth Markdown table called Top movers. Add a vitest test file app/lib/movers.test.ts with at least four positive and two negative cases against the shipped synthetic summary. Use the project's existing TypeScript and Tailwind conventions. Write the complete plan out in Markdown first; do not implement yet.

Review the plan. Answer any clarifying questions. Click Start Implementation (or switch to Agent and type Start Implementation). When it's done, run npm test in the integrated terminal — all tests should pass before you commit. Push a deliberately broken test first if you want to see the Dokploy build fail: the deploy will not proceed until the suite is green.

Ship

git add -A && git commit -m "feat: top-movers helper + vitest" && git push -u origin feat/top-movers

Merge. Watch the Dokploy build log — the RUN npm test --if-present step now actually runs Vitest and the line count of test output is real. Refresh your URL.

Re-test the same prompts

Re-send the exact prompt from before:

Show me the top movers across AMEA this cycle, ranked by absolute Net Sales delta in EUR millions.

The answer now cites the new Top movers table verbatim — same N rows, same numbers, same ordering on every retry. And locally:

npm test

Vitest now runs and prints green. Optional: break one expectation in app/lib/movers.test.ts, push it, and watch the Dokploy build fail at the test step before the container is ever built. Revert, push again, deploy succeeds. The pipeline is now genuinely guarded.

5

Feature 4 — Customize Copilot for the IBP repo

8 min

Add a .github/copilot-instructions.md plus one scoped .instructions.md so every teammate (and every Copilot session) inherits the same IBP conventions automatically.

Concept (HoL Level 5 — Custom Instructions)

Instructions files are repo-scoped meta-prompts. They ship with the code, apply to every Copilot session anyone opens against the repo, and can be filtered to specific file globs via the applyTo front-matter. This is how a team enforces "don't invent column names, use EUR millions, never put server-only code in client bundles" without re-typing it in every prompt.

Why it matters

Workshop-day quality drops the moment a second person joins the repo. Custom instructions are the cheapest, most durable answer: they turn one person's hard-won prompt discipline into a team default that survives the next refactor.

Try it first (before you implement)

In VS Code, open a fresh Copilot Chat in Ask mode (no files attached) and ask:

What stack does this project use? What's the answer shape for IBP questions? Where can I put server-only code?

Copilot will guess from package.json — generic Remix advice, no mention of EUR millions, no what changed → why → what to validate, no warning about .server.ts never being imported from a client component. Every new teammate starts here. That's the gap.

Branch & prompt

git checkout main && git pull && git checkout -b feat/copilot-instructions
Create .github/copilot-instructions.md with: (1) the project context (Remix + Vite + Tailwind + TS strict, GitHub Copilot SDK, synthetic IBP dataset, deploys via Dokploy on merge to main); (2) the domain rules from SYSTEM_PROMPT in app/lib/prompts.server.ts (EUR millions one decimal, what changed → why → what to validate, never invent numbers); (3) the WEBMAR-aligned stack rules (Remix preferred, no Next.js, no Java, no GraphQL, Prisma for ORM, PostgreSQL). Then create .github/instructions/server-only.instructions.md with front-matter applyTo: "app/**/*.server.ts" and one rule: "Never import this module from a route's client component. Always re-export through a Remix loader or action."

Ship

git add -A && git commit -m "chore: copilot instructions" && git push -u origin feat/copilot-instructions

Merge. The deploy will be a no-op (no runtime code changed) but the PR is the educational artifact — from now on every Copilot session on this repo inherits these rules.

Re-test the same prompt

Pull the merged branch (git checkout main && git pull), open a fresh Copilot Chat, and ask the exact same question:

What stack does this project use? What's the answer shape for IBP questions? Where can I put server-only code?

The answer now names Remix + Vite + Tailwind + TS strict, calls out WEBMAR rules (no Next.js, no Java, no GraphQL), states EUR millions to one decimal and the what changed → why → what to validate shape, and warns about importing *.server.ts from client routes. Same question, same model — but the repo now teaches itself.

Wrap & take-home

4 min

Every attendee leaves with a URL they can share and a clear path to point this at their own data.

  • Your URL is yours. The Dokploy project keeps running. Share it with a colleague before you leave the room.
  • To point it at your own data: replace public/ibp-data-summary.json with a JSON file of the same shape produced from your dataset, then update SYSTEM_PROMPT in app/lib/prompts.server.ts. Open a PR. Merge. Done.
  • What you really took home: not just five features, but the patterns underneath — Plan mode, custom instructions, reusable prompts, custom agents. The same patterns apply to every codebase you own.
  • To go deeper: the full reference app in this same repo shows streaming responses, persistent multi-turn sessions, and file upload. Open the source and ask IBPAnalyst to explain any piece you want.

One license, your own data, a working agent on a real URL — in one hour.

If it breaks

The five failure modes you'll actually see, in priority order.

1. Dokploy didn't redeploy after my merge

Check the Dokploy dashboard for your project. Look at the most recent deploy log. The two most common causes are a TypeScript compile error from a Copilot suggestion that npm run dev would have caught locally, or — from Feature 3 onwards — a failing Vitest run. The Docker build stage prints both: scroll to the RUN npm test --if-present step to see Vitest output. Open the failing file, ask Copilot Chat to fix the specific error message, push a fixup commit.

2. The model returns "no models available" or auth errors

The Dokploy environment variable GITHUB_TOKEN is missing the copilot scope. The facilitator regenerates it with gh auth refresh --scopes copilot && gh auth status --show-token and updates the Dokploy env. Redeploy.

3. Deploy fails with Conflict. The container name "/ibp-chat-skeleton" is already in use

Another Dokploy app on the same VM already grabbed that container name. Docker container names are host-wide unique, so two deploys cannot both call themselves ibp-chat-skeleton. Open docker-compose.yml at the root of your fork and rename the service, image, and container_name to something attendee-specific (for example ibp-chat-anna):

services:
  ibp-chat-anna:           # was: ibp-chat-skeleton
    build:
      context: ./ibp-chat
      dockerfile: Dockerfile
    image: ibp-chat-anna:latest
    container_name: ibp-chat-anna
    ...

Commit, push, redeploy. If the old ibp-chat-skeleton container belongs to a previous test of yours, you can also free the name with docker rm -f ibp-chat-skeleton from the VM — but renaming is the safer default in a shared workshop environment.

4. The deploy says it succeeded but my URL returns 404 page not found

Container is running, but Traefik has no router for your hostname. Dokploy injects the Traefik labels (traefik.http.routers.*, traefik.http.services.*) only at deploy time, and only if the Domain form has a Service Name selected. Most often the Service Name dropdown was left empty when the Domain was created, so the labels were never written.

Fix in the Dokploy UI:

  1. Open your app → Domains tab.
  2. Verify the entry: Host = your hostname · Service Name = the service from docker-compose.yml (e.g. ibp-chat-anna, not empty) · Port = 3100 · HTTPS ON with Let's Encrypt.
  3. Save.
  4. Deployments tab → Redeploy. This is required — saving the Domain alone does not regenerate the Traefik labels on the running container.
  5. Wait ~30 seconds, refresh your URL.

To confirm it's a labels issue (for the facilitator): docker inspect <container> --format '{{json .Config.Labels}}' on the VM. A healthy deploy shows ~12 traefik.* labels; a broken one shows none.

5. Every attendee gets the same error simultaneously

Copilot service issue, not your code. Switch models from the dropdown. If all models fail, the facilitator walks the room through the reference app's source on screen for the remaining time. The architecture lesson still lands.

If you're running short

Cut in this order. Each cut buys ~8 minutes.

  1. Drop Feature 4 (Stage 5). The agent is fully working at the end of Feature 3.
  2. Demo Feature 1 instead of having attendees ship it. The facilitator does the model picker as a live narrated demo; attendees only ship Features 2 and 3.

Do not cut Stages 1, 3, or 4. They are the spine: own a URL → ship a grounded agent → learn Plan mode.
